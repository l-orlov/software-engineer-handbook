# Go Concurrency

Формат: **Вопрос → короткий ответ → что сказать на Senior-уровне → follow-up**.

## Goroutines & Scheduler

**Что такое goroutine и чем она отличается от OS-потока?**
Goroutine — легковесная единица выполнения рантайма Go: стартовый стек ~2KB (растёт/уменьшается динамически), переключение контекста делает сам рантайм, а не ядро ОС. Тысячи goroutine дешевле, чем тысячи потоков ОС, потому что нет syscall на каждое переключение и стек намного меньше.

Senior: важно назвать модель **G-M-P** (Goroutine, Machine=OS thread, Processor=логический процессор с локальной очередью). Планировщик — кооперативно-вытесняющий (с Go 1.14 есть async preemption через сигналы, до этого вытеснение было только в safe-point'ах — вызовы функций, аллокации).

Follow-up: Что происходит с goroutine при блокирующем syscall?
→ M, на котором она выполнялась, блокируется вместе с ней; P отсоединяется от этого M и передаётся другому свободному/новому M, чтобы очередь goroutine на этом P не простаивала.

---

**Как работает work stealing?**
Каждый P имеет локальную очередь runnable goroutine. Когда P опустошает свою очередь, он ворует половину goroutine из очереди случайного другого P, а не лезет сразу в глобальную очередь — так меньше contention.

Senior: если не сказать про "ворует половину, а не одну" и про global run queue как fallback — это будет базовый ответ, не Senior.

Follow-up: Почему GOMAXPROCS обычно = числу ядер?
→ Больше P, чем ядер, не даёт параллелизма — только лишний scheduling overhead; меньше P — недоиспользование CPU.

## Channels

**Что происходит при `make(chan int, N)`?**
Аллоцируется структура `hchan`: кольцевой буфер на N элементов, счётчики qcount/sendx/recvx, очереди ожидающих `sendq`/`recvq` (списки goroutine, заблокированных на send/recv), mutex для защиты полей. Без буфера (N=0) — тот же `hchan`, но send блокируется, пока не появится готовый receiver (rendezvous).

Senior: подчеркнуть, что канал — это **не lock-free очередь**, а структура с обычным mutex внутри; это ответ на "почему канал иногда медленнее mutex".

Follow-up: Почему канал может быть медленнее Mutex?
→ Send/recv в канале — это mutex lock + copy данных + (иногда) переключение goroutine через scheduler. Для простого счётчика atomic/mutex — на порядок дешевле, т.к. нет копирования значения и нет обращения к scheduler'у. Каналы оправданы, когда нужна передача владения данными или синхронизация между несколькими goroutine, а не защита одной переменной.

---

**Что будет при `close(ch)` и последующих операциях?**
- Повторный `close` на уже закрытом канале → panic.
- `close(nil)` → panic.
- Send в закрытый канал → panic (`send on closed channel`).
- Recv из закрытого канала → возвращает нулевое значение сразу, без блокировки; второй возвращаемый параметр `ok` = false.
- `close` на receive-only канале (`<-chan`) → **ошибка компиляции**, недопустимо в принципе — закрывать может только владелец с правом на send.

Senior: правило "закрывает канал только отправитель, никогда получатель" — потому что получатель не может знать, есть ли ещё активные отправители.

Follow-up: Что будет с `for v := range ch`, если канал не закрыть?
→ Горутина навсегда останется в состоянии ожидания на recv (goroutine leak), если больше никто не пишет — программа не упадёт, но это утечка, которую видно в `pprof goroutine`.

---

**select с несколькими готовыми каналами — что произойдёт?**
Если готовы несколько case одновременно, Go выбирает один **псевдослучайно**, чтобы избежать systematic starvation одной из веток.

Follow-up: Как сделать неблокирующий recv?
→ `select` с `default`.

## Mutex / RWMutex / Atomic

**Когда RWMutex выгоднее Mutex?**
Когда чтений на порядки больше, чем записей, и critical section на чтение не тривиальна (иначе overhead самого RWMutex — он тяжелее обычного Mutex — съест выгоду).

Senior: RWMutex не решает «writer starvation» полностью — при постоянном потоке читателей writer может застрять надолго; в Go RWMutex это частично смягчено (после `Lock()` новые `RLock()` встают в очередь), но при высокой конкуренции это всё равно нужно иметь в виду.

Follow-up: Почему RWMutex внутри использует не банальный счётчик, а atomic + семафоры?
→ Чтобы избежать data race на самом счётчике читателей и чтобы writer мог эффективно блокироваться/будиться без busy-wait.

---

**В чём разница между atomic и Mutex по сути?**
Atomic — это одна CPU-инструкция (CAS/LOCK ADD и т.п.) без участия планировщика: подходит для одного значения (счётчик, флаг, указатель). Mutex защищает произвольный по сложности critical section, но platит за это переходом через рантайм (возможная блокировка goroutine, futex-подобный механизм внутри).

Senior: atomic не композируется — нельзя атомарно изменить два независимых поля через два отдельных atomic-вызова и получить консистентность между ними. Как только инвариант связывает несколько полей — нужен Mutex.

Follow-up: Что такое ABA problem и при чём тут atomic CAS?
→ Значение было A, изменилось на B и снова стало A; CAS этого не увидит и решит, что ничего не менялось, хотя между делом состояние проходило через B (актуально для lock-free стеков/списков на CAS).

## WaitGroup / Once / Pool / sync.Map

**Типичная ошибка с WaitGroup?**
Вызов `wg.Add(1)` **внутри** запускаемой goroutine, а не перед `go func(){...}()`. Race между `Add` и `Wait` может привести к тому, что `Wait` вернётся раньше, чем все горутины реально стартовали.

Follow-up: Что будет, если `wg.Add` уведёт счётчик в отрицательное значение (лишний `Done`)?
→ panic: `sync: negative WaitGroup counter`.

---

**Когда sync.Map лучше обычной map + RWMutex?**
Когда паттерн доступа — «пишется редко, читается часто одними и теми же ключами» (write-once/read-many, кэши) или множество горутин работают с непересекающимися ключами. sync.Map оптимизирован под это за счёт двух внутренних map (read/dirty) и copy-on-write — но не является universal replacement: под запись-тяжёлой нагрузкой обычная map + RWMutex обычно быстрее и предсказуемее.

## Context

**cancel vs timeout vs deadline — в чём разница по сути?**
`WithCancel` — отмена вручную по сигналу; `WithTimeout` — обёртка над `WithDeadline(time.Now().Add(d))`; `WithDeadline` — отмена в конкретный момент времени. Все три возвращают контекст с закрывающимся `Done()`-каналом и должны вызывать `cancel()` (иначе — утечка таймера/горутины, `go vet` про это предупреждает).

Senior: `context.Value` — не для передачи опциональных зависимостей/конфигурации, а только для request-scoped метаданных (trace id, auth-принципал). Если через context пробрасывается что-то, от чего зависит бизнес-логика функции — это антипаттерн, это должно быть явным параметром.

Follow-up: Что произойдёт, если родительский контекст отменили, а дочерний — нет?
→ Дочерний тоже отменяется: отмена распространяется вниз по дереву контекстов, но не вверх.

## Race / Deadlock / Livelock

**Почему map не потокобезопасна в Go?** *(почти гарантированно спросят)*
Плохой ответ (95% кандидатов): «потому что там race».
Senior-ответ: race — это следствие, а не причина. Запись в map может триггернуть рост хеш-таблицы и перераспределение bucket'ов (rehash). Если в этот момент другая горутина читает map, она может пройтись по структуре в промежуточном, повреждённом состоянии — это не «неверное значение», а потенциальный segfault/бесконечный цикл на уровне структуры данных. Поэтому рантайм явно детектирует одновременный read+write и **аварийно завершает процесс** (`fatal error: concurrent map read and map write`) — это не recoverable panic, специально, чтобы не дать сработать поврежденной структуре дальше.

Follow-up: Когда лучше sync.Map, а когда map+RWMutex?
→ см. секцию выше.

---

**Deadlock vs livelock vs starvation — разница?**
- **Deadlock**: все участники заблокированы навсегда, ничего не происходит (классика — циклическое ожидание двух мьютексов в разном порядке).
- **Livelock**: горутины не блокированы, активно работают, но система не продвигается (например, два процесса вежливо уступают друг другу ресурс и оба откатываются назад до бесконечности).
- **Starvation**: система в целом прогрессирует, но конкретная горутина систематически не получает ресурс (например, RWMutex с постоянным потоком читателей морит writer'а).

Follow-up: Как обнаружить deadlock в Go рантайме?
→ Если ВСЕ горутины программы заблокированы одновременно — рантайм детектирует это сам и падает с `fatal error: all goroutines are asleep - deadlock!`. Если заблокирована только часть горутин (остальные работают) — это не будет обнаружено рантаймом, нужен `pprof goroutine` или анализ дампа стека.

---

**Как работает `go test -race`?**
Race detector — это ThreadSanitizer (инструментация на уровне компилятора), который отслеживает happens-before между обращениями к памяти из разных горутин через vector clocks. Ловит **фактически произошедшие** гонки во время выполнения теста, а не потенциальные — то есть детектор ничего не найдёт, если тест не спровоцировал реальное параллельное обращение. Цена: 2-20x по памяти и времени выполнения, поэтому это dev/CI-инструмент, не для прода.

Senior: важно явно сказать «race detector не доказывает отсутствие гонок, только находит те, что реально произошли в конкретном запуске» — иначе выглядит как «прогнали -race, гонок нет = кода без гонок», что неверно.

## Практика: "что выведет этот код"

**Классическая ловушка с замыканием в цикле (Go < 1.22):**
```go
for i := 0; i < 3; i++ {
    go func() { fmt.Println(i) }() // до Go 1.22: печатает 3,3,3 (или похоже) — общая переменная i
}
```
В Go 1.22+ семантика цикла изменилась: `i` теперь per-iteration переменная, код выше стабильно печатает 0,1,2 в некотором порядке. До 1.22 фикс — передавать `i` параметром: `go func(i int) {...}(i)`.

Follow-up: Почему в этом коде вообще недетерминированный порядок вывода (0,1,2 в любом порядке), даже в 1.22+?
→ Планировщик не гарантирует порядок выполнения независимых горутин — только `sync`-примитивы или каналы дают гарантию порядка (happens-before).
