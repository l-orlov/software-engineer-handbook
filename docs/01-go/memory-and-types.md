# Go Memory & Types

Формат: **Вопрос → короткий ответ → что сказать на Senior-уровне → follow-up**.

## Slice

**Slice vs Array?**
Array — значение фиксированного размера, часть типа (`[3]int` ≠ `[4]int`), копируется целиком при передаче. Slice — дескриптор `{ptr, len, cap}` поверх массива-хранилища; передаётся дёшево (копируется только дескриптор), но два slice могут шарить один и тот же backing array.

---

**Почему `append` иногда меняет исходный массив, а иногда нет?**
Если `len(s) < cap(s)` — `append` пишет в существующий backing array по месту, и любой другой slice, смотрящий на тот же array, увидит изменение. Если `cap` исчерпан — рантайм аллоцирует новый, больший backing array (обычно ×2 для маленьких slice, для больших — рост ~1.25x), копирует данные, и исходный slice остаётся указывать на старый array. Это главный источник багов вида «функция должна была вернуть новый slice, а неожиданно испортила данные вызывающего».

Senior: явно назвать, что "capacity" — это скрытое состояние, из-за которого один и тот же код (`append`) ведёт себя по-разному в зависимости от истории использования slice — отсюда правило "не расшаривать slice между местами, где один пишет через append, а другой читает", без явного `copy` или пересоздания.

Follow-up: Как безопасно "отрезать" кусок slice, чтобы не аффектить исходные данные при дальнейшем append?
→ Использовать full slice expression `s[low:high:max]`, где `max` ограничивает cap результата так, что append в него форсированно аллоцирует новый array вместо перезаписи хвоста исходного.

---

**nil slice vs empty slice?**
`var s []int` (nil, `len=0, cap=0, ptr=nil`) vs `s := []int{}` (не nil, `len=0, cap=0`, но валидный указатель на пустую структуру). Оба ведут себя одинаково в `len()`, `range`, `append` — разница видна в `s == nil` и в JSON-сериализации (`nil` → `null`, `[]int{}` → `[]`).

---

## Map

**Как устроена map внутри (классическая реализация, до Swiss Table в 1.24)?**
`hmap` хранит массив bucket'ов; каждый bucket — 8 слотов key/value плюс указатель на overflow bucket, если 8 не хватило. Ключ хэшируется, старшие биты хэша выбирают bucket, младшие (tophash) — быстрый предфильтр внутри bucket'а, чтобы не сравнивать полные ключи зря.

Senior: overflow bucket'ы — источник деградации: при большом числе коллизий map превращается в связный список bucket'ов и теряет O(1)-характер на практике плюс это лишний random memory access (плохая cache locality).

Follow-up: Что реально произошло в Go 1.24 (Swiss Table)?
→ Новая реализация на open addressing + control bytes (метаданные о состоянии слотов хранятся отдельно и компактно, что позволяет сканировать их SIMD-инструкциями пачкой) вместо bucket+overflow. Итог — меньше cache misses, нет overflow-деградации, ниже memory overhead. Для интервью достаточно понимать концептуальный сдвиг (bucket-chaining → open addressing + SIMD-friendly metadata), без деталей probe sequence.

---

**Почему map нельзя читать и писать одновременно?**
→ см. `docs/01-go/concurrency.md` — write может триггернуть рост/rehash, что ломает структуру, поэтому рантайм детектирует и падает намеренно.

---

## Interface

**Что такое iface и eface?**
`eface` (для `interface{}`/`any`) — пара `{type-descriptor, data-pointer}`. `iface` (для интерфейса с методами) — пара `{itab, data-pointer}`, где `itab` — таблица, связывающая конкретный тип с реализацией методов интерфейса (аналог vtable), плюс сам type descriptor.

Follow-up: Почему `itab` кэшируется?
→ Построение itab для пары (конкретный тип, интерфейс) требует поиска соответствия методов — это недёшево при частой конвертации одного и того же типа в интерфейс, поэтому рантайм кэширует уже построенные itab.

---

**"Typed nil в интерфейсе" — классическая ловушка**
```go
var p *MyError = nil
var err error = p
fmt.Println(err == nil) // false!
```
`err` — это `iface{itab: *MyError, data: nil}`. Сравнение `err == nil` сравнивает всю пару (type, value), а type здесь не nil (это `*MyError`), только value nil. Отсюда `err != nil`, хотя интуитивно кажется, что должно быть nil.

Senior: практическое следствие — функция не должна возвращать `error`-интерфейс, объявленный через конкретный указательный тип, который может быть nil; либо возвращать `nil` явным литералом интерфейсного типа, а не typed-nil переменную.

Follow-up: Как правильно проверить "есть ли реальная ошибка" в таком случае?
→ Не сравнивать интерфейс с nil в отрыве от контекста — либо не давать typed nil попасть в error вообще, либо явно проверять через `errors.As`/type assertion сам указатель.

## Escape Analysis / Stack vs Heap (детально)

Это слабое место у многих — разбираем подробно, с правилами и кодом, а не одной абстрактной фразой "компилятор решает сам".

### Что такое стек и куча в контексте Go — и почему это не "два вида памяти вообще"

И стек, и куча — это просто память процесса. Разница не в том, "где физически", а в **модели владения и способе освобождения**:

- **Стек** — у каждой goroutine свой собственный стек (не общий для всей программы, как в классической модели "один стек на OS-поток"). Выделение переменной на стеке — это буквально сдвиг stack pointer на N байт при входе в функцию (`SP -= frame_size`), освобождение — сдвиг обратно при выходе. Никакой работы аллокатора, никакого GC — стоимость примерно нулевая, всё решается на этапе компиляции размером кадра функции.
- **Куча (heap)** — общая для всей программы область, управляемая аллокатором (`mallocgc`) и убираемая сборщиком мусора. Выделение здесь — это реальная работа: найти подходящий по размеру блок (size class), возможно, попросить у ОС новую страницу, зарегистрировать объект для GC.

Вопрос "где выделить переменную" **решает не программист явно** (в отличие от C, где `malloc` — это осознанный выбор), а компилятор Go — статически, во время компиляции, через **escape analysis**. Отсюда и путаница: одна и та же конструкция (`&x`, `make(...)`) может уйти либо на стек, либо в heap в зависимости от того, что происходит с этим значением дальше в коде.

### Как физически устроен стек goroutine (то, что обычно не рассказывают)

Стек goroutine — не статический блок фиксированного размера, как в потоках ОС (там обычно 1-8MB, зарезервированных заранее). У Go он:

1. **Стартует маленьким** — 2KB на новую goroutine (сильно дешевле, чем поток ОС — отсюда возможность иметь миллионы goroutine).
2. **Растёт динамически**: при входе в функцию рантайм проверяет, хватает ли места (guard page/проверка в прологе функции); если не хватает — аллоцируется новый стек **вдвое больше**, все данные **копируются** туда, и, что важно, **все указатели, ссылающиеся на старые адреса на стеке, пересчитываются** (rewrite) на новые адреса. Это возможно только потому, что рантайм точно знает, где на стеке лежат указатели (stack maps, сгенерированные компилятором) — обычный C так делать не может.
3. **Уменьшается** — при GC рантайм может решить, что goroutine давно не нуждается в таком большом стеке (использует < 1/4 от текущего размера), и сжать его.

Senior-акцент: именно возможность **переместить (скопировать) стек и переписать указатели на него** — причина, почему указатель на локальную переменную **другой goroutine** не может просто "жить как обычный указатель" через границу goroutine без специальной обработки: если бы это было разрешено без escape to heap, перемещение чужого стека сломало бы такой указатель. Поэтому: если значение может быть замечено другой goroutine (передано в канал, захвачено в closure, запущенное через `go`), оно **обязано** уйти в heap — компилятор это учитывает автоматически.

### Правило escape analysis — конкретно, не абстрактно

Компилятор для каждого значения (каждой локальной переменной, каждого результата `&expr`, `make(...)`, `new(...)`) статически строит граф "куда уходит указатель на это значение" и решает: может ли значение **пережить возврат из текущей функции** или **стать видимым другой goroutine**. Если доказать "нет" не удаётся — heap.

**Конкретные паттерны, которые форсируют escape to heap:**

```go
// 1. Возврат указателя на локальную переменную — классика
func newUser() *User {
    u := User{Name: "Alice"} // escapes to heap:
    return &u                // указатель переживает функцию
}

// 2. Запись указателя в структуру/слайс/мапу/канал, которые сами переживают функцию
func addToCache(c *Cache, u *User) {
    c.items[u.ID] = u // u escapes: попал в структуру с большим временем жизни
}

// 3. Захват переменной в closure, которая переживает функцию (например, через go)
func spawn() {
    x := 42
    go func() {
        fmt.Println(x) // x escapes: closure выполнится в другой goroutine
    }()
}

// 4. Передача в интерфейсный параметр (частая неожиданность!)
func log(v interface{}) { /* ... */ }
func f() {
    n := 5
    log(n) // n почти всегда escapes: компилятор в общем случае
           // не может доказать, что log() не сохранит интерфейс где-то дальше
}

// 5. Размер неизвестен на этапе компиляции
func makeSlice(n int) []int {
    return make([]int, n) // n — переменная, компилятор не знает размер
                           // заранее → heap, даже если слайс не "убегает" из функции
}
```

**Что остаётся на стеке (не escape):**

```go
// Значение используется только локально, не возвращается и не сохраняется наружу
func sum(a, b int) int {
    result := a + b // на стеке: живёт только пока выполняется sum
    return result   // возвращается ПО ЗНАЧЕНИЮ, не как указатель
}

// Указатель передаётся вглубь, но не "убегает" дальше того, что видит компилятор
func double(x *int) {
    *x = *x * 2 // если double инлайнится или анализируется целиком,
}               // компилятор может доказать, что x не сохраняется —
                 // тогда сама переменная на вызывающей стороне может остаться на стеке

func caller() int {
    n := 21
    double(&n) // &n может НЕ escape-нуть, если double() не убегает с этим указателем
    return n   // возвращается значение, не указатель — n можно спокойно оставить на стеке
}

// Фиксированный маленький размер, известный на этапе компиляции
func fixed() []int {
    return make([]int, 4) // константный размер, не убегает дальше → может остаться на стеке
}
```

Senior: важно проговорить, что **передача указателя в функцию не означает автоматический escape** — это самое частое заблуждение. Go делает межпроцедурный анализ (в том числе через inlining): если вызываемая функция маленькая и инлайнится, либо компилятор иначе может доказать, что указатель не сохраняется дальше её выполнения — переменная может остаться на стеке вызывающего. Escape analysis смотрит на **фактическое поведение**, не на синтаксис "тут есть `&`".

### Почему компилятор консервативен (ошибается в сторону heap)

Если компилятор не может **строго доказать**, что значение не убежит — он обязан положить его в heap, потому что ошибка в другую сторону (оставить на стеке то, что реально убежало) — это memory corruption/use-after-free, а не просто "чуть медленнее". Отсюда практические следствия:
- Прохождение значения через `interface{}` (в т.ч. `fmt.Println`, `errors.New`, generic-код до мономорфизации) — частый источник "неожиданных" heap-аллокаций, потому что анализ через границу интерфейса ограничен.
- Слишком большое значение для стека (даже если оно логически не убегает) компилятор всё равно уносит в heap — по эвристике "too large for stack frame", чтобы не раздувать стек-кадр непропорционально.

### Как проверить, что произошло на самом деле

```bash
go build -gcflags="-m" ./...      # базовый вывод: escapes to heap / moved to heap / does not escape
go build -gcflags="-m -m" ./...   # подробнее: почему именно (какая именно операция вызвала escape)
```

Follow-up: Как понять, что конкретно вызвало escape, если решений в выводе несколько по одной переменной?
→ `-m -m` печатает цепочку рассуждений компилятора (например, "escapes to heap: value passed to log(...)" со ссылкой на то, какой параметр интерфейса — виновник); `-m` без второго флага даёт только финальный вердикт без объяснения.

Follow-up: Практическое следствие для hot path кода?
→ Не "указатели — зло", а конкретно: не заворачивать горячие значения в `interface{}` без нужды (в т.ч. осторожно с логированием через `fmt`/generic-обёртками в цикле), не возвращать указатели там, где по смыслу достаточно значения, переиспользовать буферы (`sync.Pool`) вместо `make` на каждой итерации горячего цикла — и **проверять предположения через `-gcflags="-m"` и `pprof -alloc_objects`**, а не гадать на глаз, что должно было "убежать".

---

**Почему `[]byte` иногда предпочтительнее `string` в hot path?**
`string` в Go иммутабелен — любая "модификация" строки (конкатенация, `strings.Builder` без переиспользования буфера) создаёт новую аллокацию и копирование. `[]byte` можно переиспользовать и мутировать по месту (например, буфер для чтения из сети/парсинга), избегая лишних аллокаций и давления на GC. Обратная сторона — конверсия `string↔[]byte` в общем случае тоже копирует (кроме нескольких case, которые компилятор умеет оптимизировать, например `[]byte(s)` сразу как ключ map без промежуточной аллокации).

## GC (кратко — подробный deep dive не нужен для этого собеса)

**Как устроен GC в двух словах?**
Concurrent, non-generational, non-compacting **mark-and-sweep** с tri-color marking, работающий параллельно с мутатором (write barrier для корректности при конкурентных изменениях). Триггер — по умолчанию когда heap вырос в `GOGC`% (по умолчанию 100%) от размера после предыдущего GC; с Go 1.19 есть ещё soft memory limit (`GOMEMLIMIT`) как жёсткий потолок.

Follow-up: Как GC влияет на latency, и что можно с этим сделать?
→ Stop-the-world фазы в современном Go — микросекунды (в основном на старте/окончании cycle), основная работа конкурентна с мутатором, но GC отъедает CPU у полезной работы. Средства — снизить allocation rate (переиспользование буферов, `sync.Pool`, избегать лишнего escape to heap), при необходимости тюнить `GOGC`/`GOMEMLIMIT`.
