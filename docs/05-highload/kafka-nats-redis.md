# Highload: Kafka / NATS / Redis (обзорный уровень)

Формат: **Вопрос → короткий ответ → Senior-акцент → follow-up**.
Компактно — эти темы не главные на этом собесе, но базовое понимание ожидается (стек вакансии: NATS в проде, Kafka — общий бэкграунд).

## Kafka

**Что такое partition и зачем он нужен?**
Топик физически разбит на partition'ы — это единица параллелизма и **единственная гарантия порядка** (порядок сообщений гарантирован только внутри одной partition, не в топике целиком). Больше partition — больше consumer'ов может читать топик параллельно.

Senior: partition — это ещё и единица масштабирования по throughput, но нельзя "просто добавить partition" без последствий: увеличение числа partition **меняет** распределение ключей по partition (хэш от ключа % количество partition), то есть уже существующие ключи могут "переехать" на другую partition — ломает гарантию порядка для существующих ключей задним числом. Уменьшить число partition в Kafka вообще нельзя — только пересоздать топик.

Follow-up: Можно ли сделать 500 consumer'ов при 30 partition в одной consumer group?
→ Можно запустить 500 инстансов, но реально работать (получать сообщения) будут только 30 — по одному consumer'у на partition максимум внутри одной consumer group; остальные 470 будут простаивать как "горячий резерв" на случай падения активных.

---

**Consumer group, offset, rebalance — как это связано?**
Consumer group — логическое объединение consumer'ов, между которыми partition'ы топика распределяются без пересечений (каждая partition читается ровно одним consumer'ом группы). Offset — позиция consumer'а в partition (обычно коммитится в служебный топик `__consumer_offsets`). Rebalance — переприсвоение partition'ов consumer'ам при изменении состава группы (добавили/убрали consumer, consumer не прислал heartbeat вовремя) — на время rebalance обработка в затронутых partition'ах приостанавливается.

Senior: частая причина неожиданного rebalance в проде — consumer завис в обработке сообщения дольше `max.poll.interval.ms` (не прислал вовремя следующий poll) и broker считает его мёртвым, хотя процесс жив — это выглядит как "рандомные ребалансы", а на деле — слишком долгая обработка на poll.

Follow-up: Почему consumer может прочитать одно и то же сообщение дважды?
→ Consumer обработал сообщение (side-effect применён), но не успел закоммитить offset до падения/rebalance — при перезапуске/переприсвоении partition чтение продолжится с последнего закоммиченного offset, то есть с уже обработанного сообщения. Это и есть **at-least-once** по умолчанию.

---

**At-least-once vs exactly-once — что это значит технически, а не только по названию?**
- **At-least-once** — дефолт: сообщение может быть обработано больше одного раза при сбоях (см. выше), consumer обязан быть идемпотентным сам по себе (см. `docs/04-system-design/referral-and-idempotency.md`).
- **Exactly-once (EOS)** в Kafka — достигается через **idempotent producer** (producer получает `producer_id` + sequence number, broker дедуплицирует повторную отправку того же сообщения при retry producer'а на уровне partition) + **transactions API** (атомарная запись в несколько partition/топиков разом, включая offset commit как часть той же транзакции — паттерн read-process-write).

Senior: EOS в Kafka — это гарантия **в рамках самой Kafka** (producer→topic, topic→topic через Streams). Как только в пайплайне появляется внешний side-effect (запись в БД, HTTP-вызов наружу) — по-настоящему exactly-once снаружи Kafka не бывает, нужна идемпотентность на стороне этого внешнего эффекта, обычные вещи (Kafka EOS) её не покрывают.

## NATS (JetStream) vs Kafka — когда что

| | Kafka | NATS JetStream |
|---|---|---|
| Модель хранения | Log-based, retention по времени/размеру | Тоже log-based (Stream), но легче в эксплуатации |
| Порядок | Гарантирован внутри partition | Гарантирован внутри Stream (или subject при работе с ключами) |
| Latency | Выше (batching-ориентирован) | Ниже, ориентирован в том числе на request-reply в реальном времени |
| Экосистема/сложность | Тяжелее в эксплуатации, богаче tooling | Легче поднять и эксплуатировать, меньше operational overhead |
| Типичный кейс | Огромный throughput, event sourcing, стриминговая аналитика | Микросервисная коммуникация, request-reply, там где не нужен полноценный масштаб Kafka |

Senior: выбор Kafka vs NATS в реальном проекте чаще решается не "какой лучше", а **что уже есть в стеке команды** и требованиями по throughput/retention — на этой конкретной вакансии в стеке заявлен NATS, значит, стоит явно уметь объяснить, чем NATS JetStream закрывает те же задачи (Stream ≈ topic с partition'ами, Consumer ≈ consumer group), не пытаясь выдать это за Kafka.

## Redis

**TTL, SETNX и distributed lock — как из этого собрать блокировку?**
`SET key value NX PX <ttl_ms>` — атомарно "поставить, только если ключа нет" + автоматический TTL на случай, если владелец лока упадёт и не снимет его руками (без TTL — лок повиснет навсегда при падении процесса).

Senior: простой `SETNX+TTL` — это **не** строго корректный distributed lock под все случаи: если операция под локом выполняется дольше TTL, другой процесс может взять лок, пока первый ещё думает, что он им владеет (split-brain на уровне приложения). Смягчения — уникальный token-владелец при снятии лока (`DEL` только если значение совпадает с твоим token — атомарно через Lua-скрипт, чтобы избежать TOCTOU между GET и DEL) и продление TTL ("watchdog") пока операция ещё выполняется.

Follow-up: Что если нужна гарантия лока строже, чем "почти всегда работает"?
→ Redlock-алгоритм (кворум из нескольких независимых Redis-инстансов) — но это спорная в индустрии тема (известна критика от разработчика Kafka-эры distributed systems Martin Kleppmann); для большинства бизнес-задач одного Redis с token+TTL+Lua-снятием достаточно, полноценный Redlock нужен только когда цена гонки действительно высока (не просто "неудобство", а потеря денег/данных).

---

**Cache-aside vs write-through — в чём разница и когда что?**
- **Cache-aside** (самый частый паттерн): приложение само читает из кэша, при промахе — читает из БД и кладёт в кэш; при записи — пишет в БД и **инвалидирует** (не обновляет) кэш. Просто, кэш может быть временно "холодным" после инвалидации, но никогда не противоречит источнику правды дольше, чем до следующего чтения.
- **Write-through**: запись идёт одновременно в кэш и в БД (обычно через общий слой) — кэш всегда актуален сразу после записи, но усложняет логику записи и требует, чтобы этот слой был надёжным местом для обеих операций.

Senior: cache-aside — дефолтный выбор для большинства backend-сценариев именно потому, что инвалидация проще и безопаснее, чем поддержание двух источников синхронно записанными; write-through оправдан, когда read-after-write consistency критична сразу после записи, а не "через секунду".
