# Algorithms: Data Structures

Не теория ради теории — только то, что реально используется в backend-задачах и спрашивается на собесе.
Формат: короткое объяснение → сложность → когда используется → типичный вопрос интервью.

## Big O — что важно уметь, а не просто помнить таблицу

Важно уметь **на лету оценить сложность своего же кода**, который вы только что написали для задачи, а не рассказать определение. Частый косяк на собесе: не заметить скрытый O(n) внутри цикла (например, `slice = append(slice[:i], slice[i+1:]...)` в цикле — каждое удаление из середины slice — это O(n) сдвиг, весь цикл превращается в O(n²)).

Вопрос интервью: «Вы только что написали решение — какая у него сложность по времени и по памяти? Есть ли скрытые O(n) операции внутри циклов (append, copy, map iteration order)?»

## HashMap (Go: `map`)

Среднее O(1) на вставку/поиск/удаление, худший случай O(n) при массовых коллизиях (в Go есть защита от specially-crafted collision attack через randomized seed хэш-функции). Главный кейс использования в задачах — **превратить O(n²) перебор пар в O(n) за счёт "видели ли мы уже нужное значение"** (Two Sum, поиск дубликатов, группировка).

Вопрос интервью: «Почему HashMap даёт амортизированное O(1), а не гарантированное?» → рехэш при росте — редкая дорогая операция O(n), но амортизируется на все дешёвые вставки между рехэшами.

## Stack / Queue

**Stack** (LIFO) — база для: балансировка скобок, DFS итеративно (без рекурсии), вычисление выражений (RPN), "найти ближайший больший/меньший элемент справа/слева" (monotonic stack).

**Queue** (FIFO) — база для BFS, обработки задач по порядку поступления (worker pool), sliding window maximum (через deque — double-ended queue, где можно эффективно убирать элементы с обоих концов).

Вопрос интервью: «Как найти для каждого элемента массива ближайший больший элемент справа за O(n)?» → monotonic stack: идём слева направо (или справа налево), поддерживаем стек убывающих (или возрастающих) индексов, каждый элемент кладётся и снимается со стека не более одного раза → амортизированно O(n), а не O(n²) наивным перебором.

## Heap / Priority Queue (Go: `container/heap`)

Вставка/удаление минимума (или максимума) за O(log n), просмотр минимума — O(1). Используется, когда нужен постоянный доступ к "текущему лучшему" элементу при непрерывном потоке данных: **Top K элементов**, k-way merge (слияние K отсортированных потоков — актуально при мердже логов/событий из нескольких источников), очередь с приоритетом задач.

Senior-акцент: heap — это **не полностью отсортированная структура**, а только частичный порядок (родитель ≤/≥ детей) — этого достаточно для быстрого доступа к экстремуму, но обход heap не даёт отсортированную последовательность бесплатно.

Вопрос интервью: «Как найти K наибольших элементов в потоке данных, который не помещается в памяти целиком?» → min-heap размера K: держим heap из K элементов, для каждого нового элемента сравниваем с минимумом heap'а — если новый больше, заменяем. Итоговая сложность O(n log k), память O(k).

## Binary Search

Не только "поиск в отсортированном массиве" — универсальный паттерн **"поиск на монотонной функции от ответа"**: если можете за O(f(n)) проверить "подходит ли кандидат X", и предикат монотонен (все X < answer не подходят, все X ≥ answer подходят) — можно бинарным поиском найти границу за O(f(n) log n) вместо линейного перебора кандидатов.

Вопрос интервью: «Классический бинарный поиск в отсортированном массиве — на что чаще всего ошибаются кандидаты?» → на границы (`left <= right` vs `left < right`, `mid = left + (right-left)/2` вместо `(left+right)/2` — переполнение при больших индексах в языках с фиксированным int, в Go менее критично, но обсуждается) и на бесконечный цикл, если неверно двигать `left`/`right` после сравнения.

## DFS / BFS

**DFS** — обход "вглубь", естественная реализация через рекурсию или явный stack. Используется: поиск связных компонент, топологическая сортировка, обнаружение циклов, backtracking.

**BFS** — обход "по слоям" через queue. Используется всегда, когда нужен **кратчайший путь в невзвешенном графе** (DFS кратчайший путь не гарантирует).

Senior-акцент: явно сказать, почему BFS даёт кратчайший путь, а DFS — нет: BFS обрабатывает вершины строго в порядке возрастания расстояния от старта (слой за слоем), поэтому первое посещение вершины — гарантированно по кратчайшему пути; DFS может дойти до вершины длинным обходным путём раньше короткого.

Вопрос интервью: «Дан граф зависимостей задач (граф выполнения тасков) — как проверить, что нет циклической зависимости, и построить порядок выполнения?» → топологическая сортировка через DFS (post-order + reverse, или через отслеживание "серых"/"чёрных" вершин для детекции цикла) либо через Kahn's algorithm (BFS по вершинам с in-degree 0).

## Trie / Union-Find — коротко, для полноты

**Trie** — префиксное дерево, O(длина строки) на поиск/вставку независимо от количества строк в структуре; используется для автодополнения, поиска по префиксу.

**Union-Find (Disjoint Set)** — почти O(1) амортизированно (с path compression + union by rank) на "объединить две группы" / "в одной ли группе два элемента"; используется в задачах связности (Kruskal MST, "сколько островов", "сколько друзей-групп" из списка пар знакомств).
