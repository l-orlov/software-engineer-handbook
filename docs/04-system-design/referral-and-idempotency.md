# System Design: реферальная программа + идемпотентность

Формат: **Задача → ключевые решения → почему именно так (Senior) → follow-up**.
Именно то, что спросят под эту вакансию — прямое попадание в "Design Referral System".

## Design: реферальная программа

**Задача**: пользователь A приглашает B по реферальной ссылке/коду; когда B выполняет целевое действие (регистрация, первый депозит, N транзакций) — A получает бонус. Возможны многоуровневые программы (A→B→C), лимиты, разные типы бонусов.

**Ключевые компоненты:**
- `referral_codes` — код/ссылка привязана к пользователю-реферреру.
- `referral_links` — факт "B пришёл по коду A" (создаётся один раз при регистрации B, дальше неизменен).
- Триггер начисления — событие в системе (регистрация подтверждена, первый депозит завершён) публикуется в очередь (Kafka/NATS), а не начисляется синхронно в том же запросе, что и целевое действие.
- Consumer читает событие, проверяет условие бонуса, **начисляет идемпотентно** (см. ниже), пишет в `ledger`/`bonus_accruals`.

**Почему асинхронно, а не начисление бонуса прямо внутри транзакции целевого действия?**
Senior: разделение ответственности и отказоустойчивость — если начисление бонуса упадёт (баг, недоступность стороннего сервиса лояльности), это не должно откатывать или блокировать основной бизнес-процесс (регистрацию/депозит). Очередь даёт retry начисления независимо от основного потока и естественную точку для идемпотентности.

Follow-up: Что если событие "первый депозит" придёт из очереди дважды (at-least-once delivery)?
→ Ровно это и есть следующий вопрос — идемпотентность.

## Как избежать двойного начисления (идемпотентность)

**Плохой ответ**: "проверим перед начислением, было ли уже начисление" (SELECT, потом INSERT) — race condition, если два инстанса consumer'а обработают одно и то же событие параллельно (redelivery, rebalance).

**Senior-ответ**: идемпотентность обеспечивается на уровне **уникального ключа в БД**, а не проверкой в коде:
```sql
CREATE TABLE bonus_accruals (
    idempotency_key TEXT PRIMARY KEY,  -- например: event_id или hash(referrer_id, referee_id, trigger_type)
    referrer_id BIGINT NOT NULL,
    amount NUMERIC NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```
Начисление — это `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING` (см. `docs/02-postgresql/transactions-and-mvcc.md`): при повторной обработке того же события вставка молча не создаст вторую запись. Уникальный constraint — это гарантия на уровне БД, устойчивая к параллельным consumer'ам и к retry, в отличие от проверки "SELECT, потом решить".

**Откуда берётся `idempotency_key`?**
Либо `event_id` из самого события очереди (если продюсер гарантирует уникальность на событие), либо детерминированный hash от бизнес-смысла операции (`referrer_id + referee_id + trigger_type`) — так, чтобы **семантически одна и та же операция** всегда давала один и тот же ключ, независимо от того, сколько раз событие было передоставлено.

Follow-up: Чем это отличается от идемпотентности на уровне API (idempotency key в HTTP-заголовке)?
→ Принцип тот же (уникальный ключ операции + constraint/дедупликация в хранилище), просто источник ключа другой — на API его обычно передаёт клиент (чтобы повторный клик "Отправить" не задвоил запрос), в очереди событий — генерирует продюсер или выводится из содержимого события.

## Многоуровневая программа и лимиты

**Как считать бонус на нескольких уровнях (A пригласил B, B пригласил C)?**
Хранить `referral_chain` не как рекурсивный обход в момент начисления (дорого и хрупко при глубокой цепочке), а материализовать иерархию в момент регистрации: у B при регистрации записывается не только прямой referrer (A), но и, например, `referrer_level_2 = A`, если A существует у B's referrer. Начисление на каждом уровне — независимая идемпотентная операция с собственным `idempotency_key`, включающим уровень.

**Как ограничить лимит бонусов (например, не больше 100 приглашений в начисление)?**
Не проверкой `COUNT(*) FROM bonus_accruals WHERE referrer_id = X` перед вставкой (race condition при параллельных начислениях — TOCTOU), а атомарным ограничением: либо `SELECT ... FOR UPDATE` на строку-счётчик реферрера перед начислением (см. `transactions-and-mvcc.md`), либо `UPDATE referrer_stats SET count = count + 1 WHERE id = X AND count < 100 RETURNING count` — атомарная проверка-и-инкремент одним запросом, если UPDATE не вернул строку — лимит достигнут.

Follow-up: Что если лимит должен быть "мягким" (соблюдается eventual, не строго на каждой транзакции) ради масштабирования?
→ Можно считать через Redis `INCR` с последующей асинхронной сверкой с БД (eventual reconciliation) — trade-off "чуть меньше строгости, намного больше throughput", уместен, если бизнес готов на редкое минимальное превышение лимита.

## Масштабирование

**Как масштабировать обработку начислений при росте нагрузки?**
- Партиционировать очередь событий по `referrer_id` (consistent hashing по ключу) — гарантирует, что все события одного реферрера обрабатываются последовательно одним consumer'ом, что упрощает рассуждение о consistency лимитов на этого реферрера, и одновременно даёт параллелизм между разными реферрерами.
- Партиционировать таблицу `bonus_accruals` по времени (например, помесячно) — старые партиции не мешают индексам горячих данных.
- Ledger-паттерн: `bonus_accruals` — append-only, текущий баланс реферрера — материализованное представление (agregированная сумма), обновляемое инкрементально, а не пересчитываемое `SUM()` по всей истории на каждый запрос баланса.

Follow-up: Почему append-only ledger лучше, чем просто поле `balance` в таблице пользователей, которое инкрементируется на каждое начисление?
→ Ledger даёт полный аудит-трейл (кто, когда, за что начислил — критично для финансовой логики и разбора инцидентов/споров), возможность пересчитать баланс с нуля при обнаружении бага в логике начисления, и естественную идемпотентность через уникальный ключ записи — просто поле `balance` этого не даёт и требует отдельного журнала аудита сбоку, если баг всё же нужно будет расследовать.
